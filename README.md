# p2p-overlay

Защищённая оверлейная сеть на TCP, TLS 1.3 mTLS и самостоятельно реализованной Kademlia-lite DHT. Узлы обмениваются подписанными адресными записями и передают сообщения и файлы через цепочку ретрансляторов с end-to-end шифрованием.

## Требования

- Go 1.27.1
- MessagePack (`github.com/vmihailenco/msgpack/v5`) и YAML (`gopkg.in/yaml.v3`).
- PowerShell 7 и Python 3 для сценариев проверок.
- Docker Desktop с Linux-контейнерами для сетевого стенда и `tc/netem`.

## Сборка и запуск

```powershell
go build -o node.exe ./cmd/node
./node.exe internal/configs/star.yaml
```

Узел создаёт Ed25519 identity в `node.state_dir`. Повторный запуск с тем же каталогом сохраняет ключи и NodeID. Адрес bootstrap задаётся в `bootstrap.peers`; для межхостового запуска укажите доступный `node.advertise_address`. Loopback используется только для процессов на одном хосте.

```powershell
# Предварительное создание независимых ключей для стенда:
./node.exe gen-identities 15 ./run/pilot/identities
# Проверка TCP-достижимости без выполнения прикладного RPC:
./node.exe probe 127.0.0.1:9000
```

Ключи, runtime-состояние и полученные файлы не включаются в Git.

## Возможности

- TCP-кадры с заголовком 24 байта, Big-Endian, обработкой частичных чтений/записей и пределом payload 65536 байт.
- TLS 1.3 mTLS, Ed25519 identity и `NodeID = SHA-256(public_key)`. Известные контакты проверяются по ожидаемому NodeID. Первое соединение с bootstrap предполагает доверие начальному адресу.
- XOR-метрика, ограниченные k-bucket, проверка LRU через PING, итеративный lookup с ALPHA=3, bootstrap/self-lookup и refresh. Постоянного полного каталога адресов нет.
- Подписанные NodeRecord, TTL, монотонные версии, псевдонимы и детерминированное разрешение конфликтов. Репликация на три ближайших доступных хранителя, успех после двух подтверждений.
- Туннели через 2–4 разных ретранслятора, по умолчанию три; пул по умолчанию из трёх туннелей. X25519, HKDF-SHA256, AES-256-GCM и аутентифицированный ACK. После отказа маршрут перестраивается с сохранением message_id.
- Файлы до 64 МиБ, блоки до 48 КиБ, подтверждения, дедупликация, проверка размера и SHA-256.
- Выбор ретрансляторов random/rating; профиль PING с EMA успешности и задержки, последовательными отказами и подсетью. Опциональное ограничение числа ретрансляторов из одной подсети.
- Bootstrap-схемы star/ring/tree/multi-seed и отдельный стенд с реально ограниченной IP-достижимостью.

## Конфигурация

Полный пример — [internal/configs/example.yaml](internal/configs/example.yaml). Основные дополнительные настройки:

```yaml
dht:
  relay_strategy: random # random или rating
tunnel:
  relays: 3
  pool_size: 3
  ttl: 5m
  max_per_subnet: 0 # 0 выключает ограничение; 1 — один узел из /24 IPv4 или /64 IPv6
files:
  enabled: true
  download_dir: ./downloads/node-0
```

Фрагменты `files-enabled.yaml` и `files-disabled.yaml` предназначены для файлового эксперимента, а не для самостоятельного запуска узла. При отсутствии `files.enabled` сервис включён для совместимости. Каждый независимый узел должен использовать свой каталог identity и загрузок.

## Проверки

```powershell
go vet ./...
go test ./... -count=1

# Сборка, vet, тесты и матрица из 30 независимых запусков:
./scripts/run_acceptance.ps1
# Выбранная конфигурация:
./scripts/run_acceptance.ps1 -N 21 -Scheme ring -Repeats 5

# Файлы: по пять передач трёх размеров, SHA-256 и goodput:
./scripts/run_file_experiment.ps1
# Docker: random/rating, netem, проверка запрещённых TCP-пар:
./scripts/run_network_lab.ps1
# Файлы, профили, модель концентрации и сетевая матрица:
./scripts/run_extensions.ps1
```

Полная матрица использует N=15,k=3 для star/ring и N=21,k=4 для четырёх bootstrap-схем. Go-оркестратор запускает отдельные логические узлы с независимыми ключами, TCP-портами, таблицами и хранилищами. Docker-стенд отдельно проверяет независимые процессы и ограничения underlay. Сценарии сохраняют конфигурации, исходные результаты и сводки; для нового запуска выбирайте новый каталог.

`run_experiment.ps1` — вспомогательный Docker-сценарий с фиксированным ожиданием. Его структурный `verify_results.py` и остановка заранее заданных узлов не заменяют проверку сходимости и отказа фактического хранителя/ретранслятора из основного набора.

## Ограничения

Начальный bootstrap-адрес должен быть доверенным. Узлы раскрывают адреса, состав маршрута и объём трафика; анонимность и защита от глобального наблюдателя не заявляются. Ограничение подсети не защищает от распределённых Sybil и не доказывает независимость операторов.

Пул может содержать маршруты с общими ретрансляторами. Прямого fallback нет. Дедупликация действует в памяти процесса и не переживает перезапуск. Возобновление файла после смены туннеля не реализовано; незавершённые блоки удаляются с состоянием туннеля по TTL. Межузловый защищённый канал использует TLS 1.3 mTLS.

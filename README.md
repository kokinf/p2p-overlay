# p2p-overlay

Защищённая децентрализованная оверлейная сеть на основе пиринговых протоколов и Kademlia DHT. 

## Язык и библиотеки
- Go 1.27.1 (generic methods, encoding/json/v2, net, crypto/tls).
- github.com/vmihailenco/msgpack/v5 — сериализация.
- gopkg.in/yaml.v3 — конфигурация.

## 1. Сборка и тестирование

```bash
# Сборка бинарника
go build -o node.exe ./cmd/node

# Запуск всех тестов
go vet ./...
go test ./...
```

## 2. Запуск узла

Для запуска одного узла используйте конфигурационный файл:
```bash
./node.exe configs/star.yaml
```

При первом запуске узел создаст Ed25519-ключи в директории, указанной в `state_dir`, и вычислит `NodeID = SHA-256(public_key)`. При повторном запуске из этой же директории идентичность сохраняется.

### Предгенерация идентичностей для пилота

Для прогонов на `N` узлах нужны их `NodeID` до старта — они передаются как цели в `experiment.targets`:
```bash
./node.exe gen-identities 15 ./run/pilot_adv/identities
```
Команда создаёт `N` каталогов `dir/node-0 … node-(N-1)` и печатает `NodeID` в stdout.

## 3. Реализованный функционал

**Транспорт и протокол**
- TCP-транспорт с тайм-аутами `read_timeout` и `write_timeout` из конфигурации.
- 24-байтовый заголовок кадра (Big-Endian).
- Потоковый декодер, обрабатывающий частичные чтения и склеенные кадры.
- Сериализация данных: MessagePack. Сравнение с JSON — в `results/serialization.csv` (генерируется `TestSerializationComparison`).
- Кадры с `version != 1` отклоняются в `handleRPC`, узел продолжает работу.

**Идентичность и DHT**
- Долговременные Ed25519-ключи и детерминированный `NodeID`.
- XOR-метрика для вычисления расстояния между узлами.
- Таблица маршрутизации (k-buckets, `K_BUCKET_SIZE=3`, по одному на каждый бит) с LRU-политикой вытеснения.
- Итеративный алгоритм поиска (Lookup) с параллелизмом `ALPHA=3`. Каждый `LookupResult` содержит `InitialClosest` — снимок таблицы **до** поиска.
- Bootstrap-схемы: «звезда» (`star`) и «кольцо» (`ring`).
- После остановки seed-узла ранее присоединившиеся узлы продолжают выполнять `FIND_NODE` (`TestBootstrapAfterSeedShutdown`).

**Распределенное хранилище**
- Формат подписанных записей `NodeRecord` (Ed25519). Защита от подмены и отката версий.
- RPC-запросы `STORE` и `FIND_VALUE` с перенаправлением запросов к ближайшим узлам.
- Проверка `DHTKey ↔ key` на двух границах: на приёме (`STORE`) и на клиенте (`GetRecord`).
- Валидация записи: связь `NodeID ↔ pubkey`, подпись, `1 ≤ len(Addresses) ≤ 10`, формат `host:port`, `MaxRecordSize = 16 KiB`, TTL.
- Репликация записей на `R = 3` ближайших узла (кворум 2 из 3).
- Отказоустойчивость: выдача записей при отказе одного из хранителей.
- Поддержка подписанных псевдонимов (Aliases) с нормализацией и разрешением конфликтов.
- Автоматическая очистка по TTL и периодическое переопубликование владельцем с интервалом не более TTL/2.

**Защита канала**
- Межузловое взаимодействие защищено протоколом TLS 1.3 с обязательной взаимной аутентификацией (mTLS). 0-RTT отключен.
- Аутентификация использует самоподписанные X.509 сертификаты, генерируемые на лету из Ed25519-ключей.
- Жесткая привязка сертификата к `NodeID` (защита от MITM и подмены узлов).
- Защита от Replay-атак на прикладном уровне: `replayCache` по `request_id` с TTL 2 минуты. Кэш переживает переподключение, поэтому replay «из завершённой сессии» тоже отклоняется.
- Ограничение параллелизма обработчиков на узел: семафор на 64 одновременных запроса.

**Туннели и приложение**
- Построение маршрута от отправителя к получателю через заданное число ретрансляторов (по умолчанию 3, минимум 2).
- Сквозное шифрование (End-to-End) полезной нагрузки: ретрансляторы видят только ciphertext (X25519 + HKDF-SHA256 + AES-GCM).
- Стейт-машина туннеля: `BUILDING`, `ACTIVE`, `DEGRADED`, `DEAD`.
- Отказоустойчивость: при отказе ретранслятора узел удаляет его из таблицы, переводит туннель в `DEGRADED` и автоматически строит новый маршрут (`TestTunnelDeliveryAndRecovery`).
- Прикладной уровень: уникальный `message_id`, подтверждение доставки (`TunnelAck`), дедупликация повторных сообщений (защита от replay на уровне приложения).

**Экспериментальные данные**
- Каждый узел по сигналу (`experiment.enabled`) пишет `metrics-<short-id>.json`: снимок таблицы маршрутизации, все `LookupResult` (с `Trace` и `InitialClosest`), размер store. Дамп выполняется дважды — до и после экспериментальных lookup'ов.

## 4. Структура проекта

```text
cmd/node/          — точка входа в приложение, подкоманда gen-identities
configs/           — готовые конфигурации для ручного запуска
internal/config/   — парсинг YAML
internal/protocol/ — кадрирование, парсинг и сериализация (MsgPack)
internal/identity/ — Ed25519, генерация и загрузка ключей, NodeID, TLS-сертификаты
internal/nodeid/   — тип идентификатора, XOR-метрики, ParseHex
internal/dht/      — k-buckets, таблица маршрутизации, алгоритмы поиска
internal/rpc/      — обработка входящих соединений, TLS, PING/FIND_NODE/STORE
internal/records/  — модель NodeRecord, подписи, локальное хранилище и TTL
internal/tunnel/   — менеджер состояний туннелей, E2E-криптография
internal/node/     — связывание компонентов, метрики, эксперименты, логика туннелей
scripts/           — скрипты для автоматизированного запуска сети и pcap
results/           — сохранённые артефакты прогонов (CSV, JSON, pcap)
tests/             — unit- и integration-тесты
```

## 5. Автоматизированный запуск сети

Для проверки работы DHT и сходимости сети предусмотрены PowerShell-скрипты:

```powershell
# Запуск сети из 5 узлов в топологии "Звезда"
.\scripts\bootstrap_star.ps1

# Запуск сети в топологии "Кольцо"
.\scripts\bootstrap_ring.ps1

# Пилот N=15: многопереходные lookup, экспорт metrics-*.json и summary.csv
.\scripts\pilot_advanced.ps1

```

Захват pcap и проверка отсутствия открытого текста (Linux):
```bash
scripts/capture_pcap.sh lo 9000 10 results/capture.pcap
```

Логи работы узлов сохраняются в директорию `run/`.

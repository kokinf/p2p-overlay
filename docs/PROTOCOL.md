# Спецификация протокола и Модель угроз

## 1. Модель угроз (Threat Model)

При проектировании сети учитывались следующие атаки:

### Защищенные векторы атак:
1. **Пассивный перехват (Sniffing):** Злоумышленник читает трафик. *Защита:* Использование TLS 1.3 (шифрование AEAD).
2. **MITM (Man-in-the-Middle):** Попытка выдать себя за другой узел. *Защита:* mTLS с проверкой соответствия сертификата и `NodeID` (Ed25519).
3. **Подмена DHT-записи:** Злоумышленник пытается изменить адрес узла в сети. *Защита:* Все записи подписываются Ed25519 ключом владельца.
4. **Replay-атака:** Повторная отправка перехваченного валидного кадра. *Защита:* Защита на уровне TLS (счётчики сессии) + прикладной `replayCache` по `request_id` (TTL 2 минуты). Кэш переживает переподключение, поэтому replay из завершённой сессии тоже отклоняется.
5. **Откат версии (Rollback):** Попытка заменить новую DHT-запись на старую. *Защита:* Монотонное увеличение `sequence_number` в записях; `Store.Put` возвращает `ErrSequenceRollback` при `rec.Seq < existing.Seq`.
6. **Несоответствие DHT-ключа записи и запрошенного ключа:** Попытка положить запись узла A под ключом узла B. *Защита:* Проверка `rec.DHTKey() == key` на приёме (`handleRPC STORE`) и на клиенте (`GetRecord` после `Unmarshal`).
7. **Неизвестная версия кадра:** *Защита:* `handleRPC` возвращает `FrameError`, узел продолжает работу.
8. **Модификация ciphertext / значимого поля handshake:** *Защита:* TLS 1.3 AEAD; модификация приводит к ошибке чтения.

### Ограничения модели (Out of Scope):
*   **Глобальный наблюдатель:** Система не скрывает факт соединения узлов и объем трафика.
*   **Sybil-атаки:** Модель не защищает от создания большого количества фальшивых узлов.
*   **Компрометация локального узла:** Если злоумышленник получил доступ к файловой системе узла (`identity.key`), он может выдать себя за него.
*   **Сокрытие метаданных:** Размеры, временные характеристики и паттерны общения не скрываются.

## 2. Формат кадра

Каждый кадр имеет фиксированный 24-байтовый заголовок (Big-Endian):
| Поле             | Размер | Описание                                                  |
| ---------------- | ------ | --------------------------------------------------------- |
| `version`        | 1      | Версия протокола (сейчас `1`)                             |
| `type`           | 1      | Тип сообщения                                             |
| `flags`          | 2      | Служебные флаги                                           |
| `request_id`     | 16     | Уникальный ID запроса (для корреляции и защиты от Replay) |
| `payload_length` | 4      | Длина payload                                             |
| `payload`        | N      | Данные (MessagePack)                                      |

- **Версия:** кадры с `version != 1` отклоняются в `handleRPC` с `FrameError`; узел продолжает работу.
- **Длина:** `payload_length > MAX_FRAME_PAYLOAD (65536)` отклоняется **до** выделения буфера (`DecodeFrameHeader`).
- **Корреляция:** ответ должен содержать тот же `request_id`, что и запрос; иначе он не доставляется вызывающему.
- **Replay:** на приёме `request_id` попадает в `replayCache` (TTL 2 минуты). Повторный кадр с тем же `request_id` отбрасывается без вызова handler'а.

## 3. Формат записи (NodeRecord)

Запись `NodeRecord` используется для хранения адресной информации узлов и псевдонимов.

| Поле              | Тип        | Описание                               |
| ----------------- | ---------- | -------------------------------------- |
| `node_id`         | `[32]byte` | SHA-256(public_key)                    |
| `public_key`      | `[]byte`   | Публичный ключ Ed25519 (32 байта)      |
| `addresses`       | `[]string` | Массив адресов (например, "ip:port")   |
| `alias`           | `string`   | Псевдоним (опционально, нормализуется) |
| `sequence_number` | `uint64`   | Номер версии (защита от отката)        |
| `issued_at`       | `int64`    | Unix timestamp создания                |
| `expires_at`      | `int64`    | Unix timestamp истечения (TTL)         |
| `signature`       | `[]byte`   | Ed25519 подпись (64 байта)             |

### Каноническое представление для подписи
Чтобы избежать неоднозначности сериализации, подпись вычисляется над строго заданной последовательностью байт:
1. `NodeID` (32 байта)
2. `PublicKey` (32 байта)
3. Длина `Alias` (1 байт) + `Alias` в UTF-8
4. `Seq` (8 байт, Big-Endian)
5. `IssuedAt` (8 байт, Big-Endian)
6. `ExpiresAt` (8 байт, Big-Endian)
7. Для каждого адреса: Длина (1 байт) + Адрес в UTF-8

### Валидация записи
Перед сохранением и использованием записи проверяются:
- `NodeID == SHA-256(PublicKey)` — связь ключа и ID;
- Ed25519 подпись;
- `1 ≤ len(addresses) ≤ 10`, каждый адрес — `host:port` с портом `1..65535`;
- `len(alias) ≤ 128`;
- `issued_at ≤ now + 300`, `expires_at > now`, `expires_at > issued_at`;
- `len(canonical_bytes) ≤ MaxRecordSize (16 KiB)`.

### Вычисление ключа DHT
- Для узла: `Key = SHA-256("node:" + node_id_hex)`
- Для псевдонима: `Key = SHA-256("alias:" + normalize(alias))`
Нормализация: перевод в нижний регистр, удаление пробелов по краям. Строковый префикс определён в одном месте (`records.AliasKey`) и переиспользуется во всех вызывающих местах, чтобы исключить рассинхрон между `DHTKey`, `ResolveAlias` и `handleRPC STORE`.

### Разрешение конфликтов
Из нескольких валидных записей одного владельца выбирается запись с наибольшим `sequence_number`. Меньший номер считается попыткой отката (`ErrSequenceRollback`).

## 4. Сообщения RPC (Payload)

| `type` | Имя                   | Payload                                                                 |
| -----: | --------------------- | ----------------------------------------------------------------------- |
|      1 | `PING`                | —                                                                       |
|      2 | `PONG`                | —                                                                       |
|      3 | `FIND_NODE_REQUEST`   | `{target: [32]byte}`                                                    |
|      4 | `FIND_NODE_RESPONSE`  | `{contacts: [{node_id, address}]}`                                      |
|      5 | `STORE_REQUEST`       | `{key: [32]byte, record: []byte}` (record — сериализованный NodeRecord) |
|      6 | `STORE_RESPONSE`      | `{success: bool}`                                                       |
|      7 | `FIND_VALUE_REQUEST`  | `{key: [32]byte}`                                                       |
|      8 | `FIND_VALUE_RESPONSE` | `{record?: []byte, contacts?: [{node_id, address}]}`                    |
|     18 | `ERROR`               | `[]byte` — текст ошибки                                                 |
|  19–20 | `HELLO` / `HELLO_OK`  | зарезервировано                                                         |

### `STORE_REQUEST` (Тип 5)
Запрос на сохранение записи.
*Payload (MessagePack):* `key` (32 байта), `record` (сериализованный `NodeRecord`).

Сервер отклоняет запрос с `FrameError`, если:
- `rec.DHTKey() != key` — запись не соответствует запрошенному ключу;
- `rec.Validate()` вернул ошибку.

### `STORE_RESPONSE` (Тип 6)
*Payload:* `success` (bool).

Успех означает одно из:
- запись валидна и успешно сохранена;
- запись валидна, но более новая версия уже есть (идемпотентность).

### `FIND_VALUE_REQUEST` (Тип 7)
*Payload:* `key` (32 байта).

### `FIND_VALUE_RESPONSE` (Тип 8)
*Payload:* `record` (если найден) или `contacts` (массив ближайших контактов до `K`).

## 5. Lookup и его след

`FIND_NODE` / `FIND_VALUE` выполняются итеративно:
- на каждой итерации инициатор выбирает до `ALPHA = 3` непрошённых ближайших кандидатов, отправляет параллельные запросы, объединяет ответы;
- завершение — не осталось непрошенных кандидатов или найден `record`;
- таймауты/ошибки удаляют контакт из shortlist'а, поиск продолжается.

Каждый lookup оставляет `LookupResult`:

```json
{
  "target": "<hex>",
  "initial_closest": ["<hex>", "..."],
  "closest": ["<hex>", "..."],
  "rpcs": 4,
  "iterations": 2,
  "timeouts": 0,
  "errors": 0,
  "trace": [
    {"index": 0, "queried": ["<hex>"], "replies": 1, "errors": 0, "timeouts": 0}
  ],
  "started": "...", "finished": "...", "duration_ms": 43
}
```

- `initial_closest` — снимок таблицы инициатора **до** поиска;
- `closest` — итоговый shortlist;
- `trace` — по итерациям: какие узлы опрошены, сколько ответов/ошибок/таймаутов.

Это позволяет доказать, что цель отсутствовала у инициатора и была найдена через промежуточный узел.

## 6. Репликация и TTL

- `R = 3` ближайших доступных хранителей по XOR-расстоянию до ключа.
- `STORE` на каждый из них — параллельно. Успех при кворуме 2 из 3 (включая локального инициатора, если он сохранил запись).
- TTL записи — 120–300 с (по умолчанию 180). Переопубликование владельцем — не реже TTL/2 (`maintenanceLoop` ограничивает `Config.RepublishInterval` сверху через `TTL/2`).

## 7. Изменения относительно исходной версии

- Проверка `DHTKey ↔ key` на приёме (`STORE`) и на клиенте (`GetRecord`).
- Валидация версии кадра (`Frame.Version != 1 → FrameError`).
- `MaxRecordSize`, `MaxAddresses`, `validateAddress` — в `Validate`.
- Replay-кэш переживает переподключение → replay из завершённой сессии отклоняется.
- `LookupResult.InitialClosest` — снимок таблицы до поиска, доказательная база для.
- `FrameTunnelCloseOk` включён в `isResponse`, чтобы `RPC.Call` при закрытии туннеля коррелировал ответ.

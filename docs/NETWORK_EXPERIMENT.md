# Профили ретрансляторов и сетевые эксперименты

Цель — проверить выбор ретрансляторов по измеренной доступности и задержке, показать влияние контролируемой деградации на lookup и туннель, а также проверить реальное ограничение IP-достижимости. Гипотеза: задержка/потери повышают наблюдаемую задержку; рейтинг может предпочесть менее задержанные доступные узлы. Превосходство рейтинга не является условием прохождения: сохраняются все исходы, включая ошибки и отсутствие выигрыша.

```powershell
./scripts/run_network_lab.ps1
```

Команда собирает образ и последовательно запускает пять конфигураций по семь независимых Docker-процессов: random/rating в обычной сети, random/rating с netem и random в ограниченной сети. N=7, k=4, ALPHA=3, R=3, три ретранслятора и три туннеля. В сравниваемых запусках копируются одни и те же identity-ключи; runtime-состояние каждого запуска раздельное и находится под игнорируемым run/. Каталог результатов содержит конфигурации, NodeID, логи, снимки таблиц и профиль; секретные ключи не копируются в отчёт. Образ закрепляется по локальному digest, исходники фиксируются хэшами.

Для netem используется `tc qdisc replace dev eth0 root netem delay 80ms loss 2%` на node-1 и node-2. Правило действует на исходящий трафик контейнера, в том числе TLS, PING и DHT. Состояние qdisc и счётчики сохраняются. Начало нагрузки отложено на 25 секунд. Обычный и ухудшенный режимы различаются только применением этого правила; между random/rating меняется relay_strategy. Порядок пяти режимов фиксирован; случайность netem, планировщика и random-выбора не закреплена. Это функциональный пилот, не строгое причинное исследование производительности.

Каждый режим содержит шесть последовательных lookup и отправок: первая отправка включает построение пула, оставшиеся пять измеряют повторную отправку. Сырые длительности, признак успеха и номер наблюдения сохраняются в samples.csv. summary.csv содержит число попыток, число успехов и min/max/median/mean длительности успешных повторных операций. Ошибки не удаляются из знаменателя. Пять наблюдений одной сессии не являются пятью независимыми сетевыми запусками; перцентили не вычисляются.

Ограниченный underlay состоит из двух Docker internal bridge-сетей:

```text
left  172.29.211.0/24: node-0, node-1, node-2, node-3, node-4
right 172.29.212.0/24: node-4, node-5, node-6
```

Только node-4 подключён к обеим сетям; IP-forwarding между контейнерами не настраивается. Проверяются node-0 → node-4 и node-4 → node-6 (доступны), node-0 → node-6 (недоступна). `node probe host:port` выполняет настоящий TCP connect с тайм-аутом 2 секунды. Контрольная прикладная пара node-0 → node-3 находится в left; успешный обмен этой пары не является доказательством произвольной межсетевой доставки. DHT не предоставляет IP-маршрутизацию. Неуспешные обращения к недоступным контактам остаются в журнале.

Профиль хранит успехи/отказы отдельных PING, EMA успешности/задержки с alpha=0.2, последовательные отказы, время наблюдения и подсеть IPv4 /24 или IPv6 /64. При DNS-адресе подсеть неизвестна: разрешение DNS не используется как доказательство сетевой независимости. Получение профиля возвращает копию, сортировка использует один снимок. Рейтинг сначала отодвигает кандидатов с более чем двумя последовательными отказами, затем учитывает EMA успешности, задержку и NodeID при равенстве. Задержка всей цепочки не приписывается первому хопу.

## Ограничение концентрации подсети

`tunnel.max_per_subnet: 1` разрешает максимум одного ретранслятора из одной подсети в маршруте. Значение 0 отключает ограничение. При включении кандидаты с неизвестной подсетью отклоняются; нехватка различных подсетей завершает построение ошибкой без ослабления ограничения. Причины отклонения журналируются. Эта функция ограничивает концентрацию маршрута, но не гарантирует независимость владельцев узлов.

Модель проверки — атакующий уже представил 20 допустимых кандидатов из одной /24, ещё восемь кандидатов находятся в разных подсетях. TestSubnetConcentrationExperiment выполняет по 100 выборок маршрута с ограничением и без, сохраняет выбранные NodeID и число кандидатов атакующего. Проверяемый критерий: при ограничении в маршруте не больше одного кандидата атакующего. Это модель выбора маршрута после допуска контактов, а не сквозная атака Eclipse на DHT. Распределённые по подсетям Sybil, подмена объявленного адреса и независимость операторов этой мерой не решаются; счётчики модели не следует выдавать за вероятность компрометации реальной сети.

## Проверенные результаты

Итоговая серия — `results/network-lab`. Все 30 контрольных lookup нашли цель, все 30 сообщений доставлены. Для каждого сообщения журнал подтверждает три различных промежуточных узла. Верификатор независимо проверяет результат lookup по снимку трассы, получение текста узлом-получателем, три хопа, положительные TCP-контроли, запрещённую пару и наличие настроек netem.

| Режим                        | Lookup / сообщения | Среднее повторного lookup, мс | Среднее повторного сообщения, мс |
| ---------------------------- | ------------------ | ----------------------------- | -------------------------------- |
| Обычный random               | 6/6 и 6/6          | 1,4                           | 1,4                              |
| Обычный rating               | 6/6 и 6/6          | 1,2                           | 1,4                              |
| Netem random                 | 6/6 и 6/6          | 244,6                         | 348,0                            |
| Netem rating                 | 6/6 и 6/6          | 161,0                         | 1,6                              |
| Ограниченный underlay random | 6/6 и 6/6 | 1 | 1.2 |

В этой реализации выбор по рейтингу позволил избежать двух ухудшенных кандидатов при построении активного маршрута. Малый пилот с одним сетевым запуском на режим не доказывает универсального преимущества рейтинга. Исходные длительности и холодная отправка остаются в samples.csv; значения таблицы рассчитаны по пяти повторным наблюдениям каждого режима.

Полный Go-набор и vet после изменений прошли; журналы — `results/relay-regression.txt` и `relay-vet.txt`. Сырые 200 выборок модели концентрации сохранены в `results/relay-validation/subnet-selection.json`: без лимита 38 из 100 маршрутов состояли целиком из условно атакующих кандидатов, с лимитом — 0 из 100. Проверяются также копирование профиля, конкурентные обновления, IPv4/IPv6-префиксы и предпочтение работоспособных кандидатов. В итоговую статистику включена только полная серия network-lab; промежуточная диагностическая серия удалена.

Каждый созданный Docker-проект остановлен после измерений. Для нового полного запуска файлов, профилей и сетевой матрицы используется `scripts/run_extensions.ps1`. Сценарии требуют новый каталог результатов и не перезаписывают существующую серию.

## Привязки bootstrap

Текущий генератор записывает pins публичных NodeID bootstrap-соседей из локально созданных identity, а не узнаёт их из первого сетевого соединения. Актуальный сохранённый network-lab запуск выполнен с этими pins. Входящий допуск по умолчанию open; allowlist требует отдельно согласованных NodeID клиентов. Правила доверия см. TRUST_MODEL.md.
